    0. Words You Will See Often (Mini Glossary)

    Word Simple meaning
    JPA A specification: a set of rules and interfaces (EntityManager, @Entity, ...) for talking to a database from Java. It is just the rulebook.
    Hibernate The actual library that follows those rules. When you use JPA in Spring Boot, Hibernate does the work underneath.
    Spring Data JPA A layer on top that gives you JpaRepository so you don't write boilerplate.
    Entity A Java class mapped to a table. One object = one row.
    Session / EntityManager The object you use to talk to the database. EntityManager is the JPA name, Session is the Hibernate name. They are the same thing for our purposes.
    Persistence context The "workspace" the Session keeps in memory while you work. (Topic 1 is all about this.)
    Transaction A group of database operations that either all succeed (commit) or all get undone (rollback).
    Flush Sending the pending SQL to the database (without committing).
    Commit Making the transaction's changes permanent and visible to others.
    Proxy A stand-in object that looks like an entity but loads real data only when you use it.
    Round trip One request from your app to the database and back. Each one costs time.

    1.2 Entities

    java
    @Entity
@Table(name = "orders")
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "orders_seq")
    @SequenceGenerator(name = "orders_seq", sequenceName = "orders_seq", allocationSize = 50)
    private Long id;

    // Many orders belong to one user. LAZY = don't load the user until someone asks (Topic 3).
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "user_id")
    private User user;

    @Enumerated(EnumType.STRING)          // store "PAID" not 1, so reordering the enum is safe
    @Column(nullable = false, length = 20)
    private OrderStatus status = OrderStatus.NEW;

    @Column(nullable = false)
    private BigDecimal total = BigDecimal.ZERO;

    @Version                              // Hibernate bumps this on every update (Part 2)
    private long version;

    // One order has many items. mappedBy = the "items" side does NOT own the foreign key;
    // OrderItem.order does.
    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderItem> items = new ArrayList<>();

    protected Order() {}                  // JPA needs a no-arg constructor (protected is fine)

    public Order(User user) { this.user = user; }

    // Keeps BOTH sides of the relationship in sync in memory.
    public void addItem(OrderItem item) {
        items.add(item);
        item.setOrder(this);
    }
}

@Entity
@Table(name = "order_items")
public class OrderItem {
    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "order_items_seq")
    @SequenceGenerator(name = "order_items_seq", sequenceName = "order_items_seq", allocationSize = 50)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "order_id")
    private Order order;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "product_id")
    private Product product;

    private int quantity;
    private BigDecimal unitPrice;
}

    Topic 1: Persistence Context, Entity States, First-Level Cache (+)

    1.1 The big idea

    The problem without an ORM

    With plain JDBC, you run SELECT, loop through the rows, and build Java objects yourself. Three annoying questions appear:

    1. Same row, two objects? If you load order #42 twice, do you get two separate Java objects? If you edit both, which one wins?
    2. What changed? If you load 500 orders and change 3 fields on 2 of them, who figures out which UPDATE statements to run?
    3. When to write? Should every setStatus() immediately hit the database? That would be slow.

    The solution: the persistence context

    Analogy: a workbench.
    You go to a warehouse (the database) and borrow some items. You put them on your workbench (the persistence context). While they are on the bench:

    • Each item appears only once (no duplicates of the same item).
    • Hibernate took a photo of each item when you picked it up.
    • You modify items freely. Nothing goes back to the warehouse yet.
    • At the end (commit), Hibernate compares each item to its photo, sees what changed, and sends only the needed updates to the warehouse.

    So the persistence context is:

    • a map from (entity type, id) to the object in memory (one object per row),
    • plus a snapshot (the "photo") of each object's values when it was loaded,
    • plus a queue of pending SQL statements.

    It is also called the first-level cache (L1), because it remembers objects you already loaded.

    Who is responsible for what?

    Who Responsibility
    JPA (the rulebook) Defines the idea of a persistence context and the entity states
    Hibernate (the library) Implements it with classes like Session, StatefulPersistenceContext, EntityEntry, ActionQueue
    Spring Decides when a persistence context opens and closes (usually: one per transaction)

    1.2 Entity states: the life of a Java object

    Every entity object is in one of four states.

    State Simple meaning Analogy
    Transient (JPA calls it "new") Just created with new. Hibernate doesn't know about it. No row in the DB. A product still in your hand, not yet put on the shelf
    Managed (persistent) On the workbench. Hibernate watches it and will save changes. An item on your workbench
    Detached Has a row in the DB, but the workbench is gone (transaction ended) or you removed it from the bench. Hibernate no longer watches it. An item you took home from the workbench; changes you make at home are not tracked
    Removed Marked for deletion. The DELETE runs at flush. An item with a "to be discarded" sticker
    Mermaid Diagram — Entity States
    stateDiagram-v2
    [*] --> Transient: new Order()
    Transient --> Managed: persist()
    Managed --> Removed: remove()
    Removed --> Managed: persist() again (cancels delete)
    Managed --> Detached: detach() / clear() / transaction ends
    Detached --> Managed: merge() (gives back a NEW managed copy)
    Removed --> [*]: flush runs the DELETE

    Rules beginners often get wrong

    • persist() on a detached entity throws an exception. persist is only for brand-new objects.
    • remove() on a detached entity throws an exception. Load it or merge it first.
    • merge() does NOT reattach the object you pass in. It finds (or loads) the managed copy with the same id, copies your values onto it, and returns that copy. Your original object stays detached.
    java
    Order detached = ...;                 // came from an earlier transaction
em.merge(detached);                   // WRONG: result thrown away
detached.setStatus(PAID);             // changes a detached object, so nothing is saved

Order managed = em.merge(detached);   // CORRECT: use the returned object
managed.setStatus(PAID);              // tracked
    • Hibernate-specific update()/saveOrUpdate() are deprecated in Hibernate 6 and removed in Hibernate 7. Use the standard JPA methods.

    1.3 What is inside the persistence context?

    You don't need to memorize class names, but this picture helps when reading stack traces and heap dumps.

    Mermaid Flowchart — Inside the Persistence Context
    flowchart TB
    EM["EntityManager (JPA)"] --> S["Session (Hibernate)"]
    S --> PC["Persistence Context"]
    S --> AQ["Action Queue: pending INSERT / UPDATE / DELETE"]
    S --> CONN["JDBC Connection (from Hikari pool)"]
    PC --> MAP["Map: (type, id) -> entity object"]
    PC --> EE["EntityEntry per object: status, id, snapshot, version"]
    PC --> PRX["Proxies (lazy stand-ins)"]
    • The map is why find(Order.class, 42) twice gives the same object.
    • EntityEntry stores the snapshot (an array of the values at load time) and the current status.
    • The action queue is why persist() usually doesn't run SQL immediately.

    Memory cost: each managed entity costs roughly 2-3 times its own size (object + snapshot + bookkeeping). Loading 500,000 entities in one transaction is therefore a memory problem, not just a speed problem (see Topic 15).

    1.4 Step-by-step: what each operation really does

    1.4.1 em.find(Order.class, 42L)

    1. Hibernate checks the persistence context: "Do I already have order 42 on the bench?"
    2. Yes: return the same object. No SQL runs.
    3. No: (optionally check the second-level cache, Part 2), otherwise run SELECT ... FROM orders WHERE id = 42, create the object, take the snapshot, put it on the bench, return it.

    1.4.2 Queries (JPQL/HQL) are different

    This is a very common misunderstanding:

    java
    Order a = em.find(Order.class, 42L);                 // SELECT runs
a.setStatus(OrderStatus.PAID);                       // change in memory only

Order b = em.createQuery("select o from Order o where o.id = 42", Order.class)
            .getSingleResult();                      // a SELECT runs again

assert a == b;                                       // the SAME object

    Two facts:

    1. A query always goes to the database. Only find()/getReference() (lookup by id) check the bench first.
    2. For each row the query returns, Hibernate asks: "Do I already have this entity on my bench?" If yes, it returns the existing object and ignores the new column values from the row.

    So within one transaction, the data you see can be older than what the database holds now (if someone else committed a change, or you ran a bulk update). The persistence context behaves like a "frozen view" of the entities you loaded. If you really need fresh data, call em.refresh(entity).

    1.4.3 persist() (saving a new object)

    For our SEQUENCE ids:

    1. Hibernate assigns an id from a pre-fetched block of 50 ids (it calls the database sequence only once per 50 ids).
    2. The object becomes managed.
    3. An INSERT is queued.
    4. No SQL is sent yet.

    If the id strategy were IDENTITY (id created by the database during INSERT), Hibernate must send the INSERT immediately to learn the id. That removes the "delay and batch" advantage. Topic 12 covers it.

    1.4.4 merge()

    Mermaid Sequence Diagram — merge()
    sequenceDiagram
    participant App
    participant S as Session
    participant DB
    App->>S: merge(detachedOrder with id=42)
    S->>S: Is order 42 on the bench?
    alt not on the bench
        S->>DB: SELECT ... WHERE id=42
    end
    S->>S: copy values from detached object onto managed one
    S-->>App: return the managed object

    merge() needs the target loaded, which usually costs an extra SELECT.

    1.4.5 remove()

    The object's status becomes DELETED and a DELETE is queued. With cascade = REMOVE or orphanRemoval, its children are deleted first. The SQL runs at flush time.

    1.5 How Spring decides when the persistence context lives

    When you inject EntityManager or use a Spring Data repository, you are really using a shared proxy. On every call, it looks for the EntityManager attached to the current transaction.

    • Inside @Transactional: Spring opens an EntityManager, starts a database transaction, and keeps them together until the method ends. The persistence context lives for the whole transaction. Two repository calls in the same method share it, so userRepo.findById(1) twice causes one SELECT and returns the same object.
    • Outside a transaction: each repository call gets a tiny, short-lived EntityManager. Anything it returns is detached immediately. Writes fail with TransactionRequiredException.
    • With Open Session In View (OSIV): the persistence context lives for the whole web request (Topic 4). We disable it.

    Misconception: "A repository has its own cache." No. A repository is a thin wrapper over the same EntityManager. The "cache" is the persistence context of the current transaction.

    1.6 Practical code: seeing identity and delayed writes

    java
    @Service
@RequiredArgsConstructor
public class OrderDemoService {

    private final EntityManager em;

    @Transactional
    public void demo() {
        // getReference: no SQL. Returns a lazy stand-in (proxy). We only need its id as a foreign key.
        User user = em.getReference(User.class, 1L);

        Order order = new Order(user);                                    // state: TRANSIENT
        order.addItem(new OrderItem(em.getReference(Product.class, 10L), 2, new BigDecimal("19.99")));

        em.persist(order);                                               // state: MANAGED, id assigned, no INSERT yet
        log.info("id = {}", order.getId());                              // id already available

        order.setStatus(OrderStatus.PAID);                               // memory change only

        Order same = em.find(Order.class, order.getId());                // found on the bench, no SELECT
        assert same == order;
    }   // commit -> flush -> INSERT orders (status already PAID), INSERT order_items
}

    Simplified SQL log:

    sql
    select nextval('orders_seq')            -- only when the pool of 50 ids runs out
select nextval('order_items_seq')
insert into orders (status, total, user_id, version, id) values (?, ?, ?, ?, ?)
insert into order_items (order_id, product_id, quantity, unit_price, id) values (?, ?, ?, ?, ?)

    Notice: the order is inserted once with status PAID. The change from NEW to PAID happened before the flush, so no extra UPDATE was needed. Delaying writes lets Hibernate send fewer statements.

    1.7 What does save() do in Spring Data?

    repository.save(entity) is just:

    java
    if (entityInformation.isNew(entity)) { em.persist(entity); return entity; }
else                                  { return em.merge(entity); }

    How does Spring decide "new"?

    1. If the entity has a wrapper-type @Version field (Long, not long): new when it is null.
    2. Otherwise, if the id is a primitive: new when the id is 0.
    3. Otherwise: new when the id is null.

    The assigned-id trap

    If you assign ids yourself (for example UUID.randomUUID()), the id is never null on a brand-new object. Spring thinks "not new", calls merge(), and every insert becomes a SELECT followed by an INSERT. That can double your insert cost.

    Fix: tell Spring when the entity is new.

    java
    @Entity
public class Payment implements Persistable<UUID> {
    @Id private UUID id = UUID.randomUUID();

    @Transient private boolean isNew = true;       // not stored in the DB

    @Override public UUID getId() { return id; }
    @Override public boolean isNew() { return isNew; }

    @PostPersist @PostLoad
    void markNotNew() { this.isNew = false; }      // after saving or loading, it is no longer new
}

    1.8 find() vs getReference()

    find getReference
    SQL Immediately (unless already on the bench) None until you touch a non-id field
    If the row doesn't exist Returns null Throws EntityNotFoundException later, on first use
    Typical use You need the data You only need to set a foreign key
    java
    order.setUser(em.getReference(User.class, userId));   // no SELECT on users, just user_id in the INSERT

    If you are going to read fields anyway, use find. A proxy would just add a second, lazier SELECT.

    1.9 Common mistakes

    1. Calling save() on an entity you just loaded "to be safe". It is unnecessary. The UPDATE comes from dirty checking at flush, not from save(). It also misleads readers.
    2. Ignoring the return value of merge().
    3. Huge transactions that load too many entities (memory and slowness).
    4. Treating the persistence context as a cache across requests. It lives for one unit of work. Caching across requests is the second-level cache (Part 2).
    5. Changing an entity after its transaction ended and expecting it to save.
    6. Using entities as API request bodies and calling save(). A client could overwrite fields you never meant to expose, and merge writes full rows.

    1.10 Real-world case study: the nightly job that gets slower and slower

    Situation. A nightly job recalculates totals for 400,000 orders. It loads orders in pages inside one @Transactional method and updates each.

    Symptoms. The first 10,000 orders take 20 seconds. By 200,000 the speed is 10 times slower. Memory climbs, garbage collection eats 40% of the time, and eventually OutOfMemoryError.

    Root cause (simple explanation).

    • Every loaded order stays on the workbench. Nothing is ever removed.
    • Before each query, Hibernate flushes, and a flush checks every object on the bench for changes.
    • So the 1st chunk checks 500 objects, the 2nd checks 1,000, the 800th checks 400,000. Total work grows like N × N.

    How to investigate.

    • Heap histogram: jcmd <pid> GC.class_histogram | head -20 shows Order, OrderItem, Object[] (snapshots) and Hibernate EntityEntry objects dominating.
    • Hibernate "Session Metrics" log at the end of the transaction shows a huge number of flushes and "flushing a total of ... entities".
    • A CPU profiler shows time in DefaultFlushEntityEventListener and findDirty.

    Fix. Process in chunks so the bench is emptied regularly:

    java
    public void run() {
    while (true) {
        List<Order> chunk = txTemplate.execute(status -> {
            List<Order> orders = repo.findChunk(...);        // 500 rows
            orders.forEach(Order::recomputeTotal);
            return orders;
        });                                                  // commit here: bench is cleared, memory freed
        if (chunk.size() < 500) break;
    }
}

    Alternatives: call flush() then clear() inside one transaction; use a single SQL UPDATE; or use StatelessSession. All of these are covered in Topic 15.

    Lesson. The persistence context is a working set. Keep it small.

    1.12 Best practices

    • Open transactions in the service layer, and keep them short.
    • Use persist (through save with generated ids) for new objects. For updates: load, change, and let dirty checking save it.
    • Return DTOs (simple data objects) from services, not managed entities.
    • Keep the bench small for bulk work.
    • Use getReference only to set foreign keys.

    1.13 Key takeaways (Topic 1)

    • The persistence context = identity map + snapshots + delayed-write queue.
    • find checks the bench first. Queries always hit the DB, but the objects they return are matched against the bench (the first instance wins).
    • persist() and remove() only schedule work. Flush executes it.
    • merge() copies values onto a managed instance and returns it.
    • In Spring (without OSIV) the persistence context lives exactly as long as the transaction.

    Topic 2: Flushing, Dirty Checking, Read-Only Transactions, equals/hashCode (+)

    This topic has four parts. Each is explained on its own.

    Part 2A: Flushing

    2A.1 The big idea

    Analogy: typing a document.

    • Changing text in the editor = changing your entity in memory.
    • Flush = pressing "Save" to a draft file on your own computer. Only you see the draft.
    • Commit = publishing it for everyone.
    • Rollback = deleting the draft.

    Flush sends the pending SQL to the database inside your current transaction. It does not commit. Other transactions can't see flushed rows until you commit (PostgreSQL isolates them), but your own transaction can see them. If you roll back, everything flushed is undone.

    2A.2 When does a flush happen?

    1. At commit. Spring flushes just before committing.
    2. Before a query, in the default mode AUTO, if the query might be affected by your pending changes.
    3. When you call it: em.flush(), repository.flush(), saveAndFlush().

    2A.3 How AUTO flush decides (important and often confusing)

    Hibernate wants queries to see your own pending changes ("read your own writes"). So before running a query, it may flush first.

    • JPQL/HQL queries: Hibernate looks at which tables the query touches. If you have pending changes on those tables, it flushes first. A query on Product won't force a flush of a pending Order change.
    • Native SQL queries: Hibernate cannot read your SQL to know the tables, so (in Spring Boot with JPA) it plays safe and flushes everything. Declare the affected tables if you want precision.
    • FlushModeType.COMMIT: flush only at commit. Your queries might not see your own pending changes. Rarely a good idea.
    • Hibernate-only FlushMode.MANUAL: never flush unless you ask. Spring uses this for read-only transactions (see Part 2C).
    java
    @Transactional
public void autoFlushDemo(Long orderId) {
    Order o = em.find(Order.class, orderId);
    o.setStatus(OrderStatus.PAID);              // pending change on the orders table

    // This query reads the orders table, so Hibernate flushes first:
    long paid = em.createQuery("select count(o) from Order o where o.status = 'PAID'", Long.class)
                  .getSingleResult();
    // SQL order: UPDATE orders SET ...;  then SELECT count(*) FROM orders ...
}
    java
    @Transactional
public void otherTable(Long orderId) {
    Order o = em.find(Order.class, orderId);
    o.setStatus(OrderStatus.PAID);

    // This query reads products only. No overlap, so NO flush. The UPDATE stays pending.
    em.createQuery("select p from Product p", Product.class).getResultList();
}

    2A.4 What happens during a flush

    Mermaid Flowchart — Flush Steps
    flowchart LR
    A[Flush starts] --> B["Cascade to new objects reachable from managed ones"]
    B --> C["Dirty-check EVERY managed entity, queue UPDATEs"]
    C --> D["Queue collection changes"]
    D --> E["Execute the queue in a fixed order"]
    E --> F["Refresh snapshots"]

    2A.5 The fixed execution order (very important)

    Hibernate does not run SQL in the order you wrote your code. It runs the queue in this order:

    1. Orphan removals
    2. Entity INSERTs
    3. Entity UPDATEs
    4. Collection removals
    5. Collection updates
    6. Collection inserts
    7. Entity DELETEs

    Real consequence. Suppose a unique constraint exists on (order_id, product_id). You write:

    java
    em.remove(oldItem);              // DELETE of the row with unique value X
em.persist(newItem);             // INSERT of a new row with the SAME unique value X

    At flush, the INSERT runs before the DELETE. The database rejects it with a unique constraint violation. Fix: call em.flush() between the two lines, or update the existing row instead.

    Another consequence: errors show up late. A constraint violation appears at flush or commit, not at persist(). The stack trace may point at Spring's transaction code instead of your business logic. When debugging, temporarily use saveAndFlush() or em.flush() to make the error appear at the line that caused it.

    2A.6 PostgreSQL-specific: one error ruins the whole transaction

    In PostgreSQL, if any statement in a transaction fails, the transaction becomes aborted. Every following command fails with:

    log
    ERROR: current transaction is aborted, commands ignored until end of transaction block

    Hibernate also treats the session as unusable after a flush failure. So this common pattern does not work:

    java
    @Transactional
public void importUsers(List<User> users) {
    for (User u : users) {
        try {
            em.persist(u);
            em.flush();                       // fails on a duplicate email
        } catch (PersistenceException e) {    // WRONG: the transaction is already doomed
            log.warn("skipping {}", u.getEmail());
        }
    }
}

    Correct alternatives:

    • Check or filter duplicates before inserting.
    • Use native SQL INSERT ... ON CONFLICT DO NOTHING.
    • Process each item in its own transaction (this needs a call through another Spring bean, because of the "self-invocation" rule in Part 2).

    2A.7 Flush mode decision table

    Mode Flushes when Use when Risk
    AUTO (default) At commit, and before queries that overlap pending changes Almost always With a big persistence context, many flushes become slow
    COMMIT Only at commit or when you call it You don't need to read your own pending writes Queries miss your own changes
    MANUAL (Hibernate) Only when you call flush() Read-only work, controlled bulk loops You may forget to flush and silently lose changes
    Explicit flush() When you call it You want errors early, or ordering workarounds, or batching windows Overuse kills the delayed-write benefit

    Part 2B: Dirty Checking

    2B.1 The big idea

    Analogy: spot-the-difference.
    When an entity is loaded, Hibernate takes a photo (snapshot). At flush time, it compares the current object to its photo. Any difference becomes an UPDATE.

    That is why you don't write repository.save() after changing a managed entity. Hibernate notices the difference itself.

    2B.2 How it works step by step

    1. At load: Hibernate copies the property values into an array (loadedState) inside the object's EntityEntry.
    2. At flush: for each managed entity, compare each property to the snapshot value.
    3. If something differs, queue an UPDATE for that entity.

    Cost:

    • Time: (number of managed entities) × (number of properties), every flush.
    • Memory: one snapshot array per managed entity.

    That is why large persistence contexts are slow (Case Study 1).

    2B.3 Which columns does the UPDATE include?

    By default, Hibernate updates all mapped columns, even if only one field changed:

    sql
    update orders set status=?, total=?, user_id=?, version=? where id=? and version=?

    Why? The SQL text is generated once at startup and reused. That helps statement caching and JDBC batching (Topic 13).

    @DynamicUpdate (Hibernate-specific) builds the UPDATE per case with only the changed columns:

    sql
    update orders set status=?, version=? where id=? and version=?
    Default (all columns) @DynamicUpdate
    Statement reuse and batching Excellent (one SQL shape) Poor (many shapes)
    Tables with big text / bytea / jsonb columns Rewrites the big values on every update Writes only what changed
    Does it prevent lost updates? No (use @Version, Part 2) No, not a substitute for locking
    Use when Typical narrow entities Wide rows with large JSON or text columns

    PostgreSQL note: an UPDATE always creates a new row version internally (MVCC), however few columns changed. So @DynamicUpdate doesn't make PostgreSQL's per-row work cheaper. It only changes the statement shape and avoids rewriting big values.

    2B.4 Ways to make dirty checking cheaper

    • Keep the persistence context small (the best fix).
    • Use read-only entities or queries (Part 2C).
    • Bytecode enhancement with dirty tracking: the entity records changes itself, so Hibernate skips the full comparison. Needs a build plugin.

    2B.5 Surprises with dirty checking

    1. Phantom UPDATEs. If a custom converter (for example JSON to object) creates a new object each time and has no proper equals, Hibernate thinks the value changed and issues an UPDATE for every loaded entity. How to notice: Hibernate's entityUpdateCount rising on a read-only endpoint, or pg_stat_user_tables.n_tup_upd growing with read traffic.
    2. Replacing a collection. Doing order.setItems(new ArrayList<>()) replaces Hibernate's tracked collection and can cause delete-all-and-reinsert or the error "A collection with cascade=all-delete-orphan was no longer referenced". Mutate the existing collection (clear() then addAll()), ideally inside a domain method.
    3. @Version and collections. Changes to a collection the entity owns (not mappedBy) bump the entity's version. Changes to an inverse mappedBy collection do not.
    4. @PreUpdate runs at flush for dirty entities, at a time Hibernate chooses. Don't put business logic with side effects in it.

    Part 2C: Read-Only Transactions

    2C.1 The big idea

    @Transactional(readOnly = true) tells "this method only reads". It is a hint passed down several layers, and each layer reacts differently. This is where most misunderstandings come from.

    2C.2 What each layer does (Spring Boot 3, Hibernate 6)

    Layer What happens
    Spring Marks the transaction as read-only. It only has effect when it starts a new transaction. If your method joins an existing read-write transaction, the hint is ignored.
    Hibernate Sets flush mode to MANUAL (no automatic flush) and loads entities as read-only: no snapshot kept and no dirty checking.
    JDBC / pgjdbc Sets the connection to read-only, which sends BEGIN READ ONLY to PostgreSQL.
    PostgreSQL Rejects writes in that transaction: ERROR: cannot execute INSERT in a read-only transaction.
    Routing (only if you set it up) A routing DataSource can send read-only transactions to a replica. That is your own configuration, not a default (Part 3).

    Verify the internals against your exact Spring and Hibernate versions before relying on a specific detail.

    2C.3 Why use it?

    1. Faster read paths: no snapshots, no dirty checks, no flush before each query.
    2. A safety net: PostgreSQL itself rejects real writes.
    3. Clear intent for the reader.

    It does not change the isolation level and does not make the database itself read faster.

    2C.4 The trap: silently lost changes

    java
    @Transactional(readOnly = true)               // "it's just a lookup"
public OrderDto getAndMarkViewed(Long id) {
    Order o = repo.findById(id).orElseThrow();
    o.setLastViewedAt(Instant.now());          // you expect this to be saved
    return mapper.toDto(o);
}

    Result: no UPDATE and no error. Flush mode is MANUAL and the entity is read-only, so Hibernate never writes it. Even worse, if an outer read-write transaction already loaded the entity, the same code might save it. The behavior then depends on who called it, which is very hard to debug.

    Case study 2: "The order status sometimes isn't saved"

    Situation. A payments service marks orders PAID after gateway callbacks. During a performance cleanup, someone put @Transactional(readOnly = true) on the whole OrderService class. One write method forgot to override it with a plain @Transactional.

    Symptoms. Intermittent: callbacks return 200, but some orders stay NEW. No exceptions.

    Root cause. The write method inherited read-only. Hibernate's MANUAL flush meant changes were never written. It worked "sometimes" because some callers already had a read-write transaction, which the method joined (the read-only hint was ignored).

    How to investigate.

    • Enable org.springframework.transaction.interceptor: TRACE and look for the transaction definition: PROPAGATION_REQUIRED,ISOLATION_DEFAULT,readOnly.
    • Hibernate statistics: entityUpdateCount didn't change during the request.
    • PostgreSQL: pg_stat_statements shows fewer UPDATE calls than callbacks.

    Fix. Put @Transactional (read-write) explicitly on write methods. Pick one convention (for example, write by default and readOnly = true on query methods) and enforce it. Add an integration test that checks the database state after the write method.

    Prevention. A test that counts UPDATE statements (Part 2, Topic 23) catches this class of bug.

    2C.5 Best practices

    • Mark query-only service methods @Transactional(readOnly = true).
    • Don't treat it as security. Database roles and grants are the real protection.
    • Remember it's ignored when joining an existing writable transaction.
    • If you route reads to replicas, beware of replication lag (stale data); never send a "read right after my own write" flow to a replica (Part 3, Topic 46).

    Part 2D: equals() and hashCode() for Entities

    This is the hardest part of Topic 2, so we go slowly.

    2D.1 Why does it matter?

    equals and hashCode are used by:

    • HashSet, HashMap
    • Hibernate's collection handling for Set associations
    • your own code when comparing entities across different sessions (for example, a detached copy against a fresh one)

    Within one persistence context, == already works, because there is only one object per row. The problems appear with detached entities, sets and proxies.

    2D.2 A refresher: how a HashSet works

    Analogy: a coat check with numbered racks.
    When you add an object to a HashSet, Java calls hashCode() and puts the object on the rack with that number. To find it later, Java calls hashCode() again and looks on that rack. If the number changes after you put it away, Java looks on the wrong rack and the object seems lost.

    That is the core rule: hashCode must not change while the object is inside a hash-based collection.

    2D.3 The central difficulty

    A new entity has no id yet (id == null). After persist(), it gets an id. If hashCode uses the id, it changes:

    java
    @Override public int hashCode() { return Objects.hash(id); }   // BAD with generated ids
    java
    Set<OrderItem> items = new HashSet<>();
OrderItem item = new OrderItem(...);   // id == null  -> hash A (rack A)
items.add(item);                       // stored on rack A
em.persist(item);                      // id assigned  -> hash is now B
items.contains(item);                  // FALSE: Java looks on rack B. The item is "lost"

    2D.4 Other traps

    Trap Why it breaks
    getClass() != o.getClass() in equals A Hibernate proxy is a generated subclass, so a proxy never equals the real entity. Use instanceof, and use getters (not fields) since proxy fields are empty.
    Lombok @Data or @EqualsAndHashCode on entities Includes all fields: loads lazy associations (hidden queries or LazyInitializationException), loops forever on two-way associations (StackOverflowError), and changes whenever data changes.
    Putting mutable fields (like status) in hashCode Hash changes while in a set.
    equals on all fields The same row loaded at different times looks "different".
    Lazy associations inside toString() Logging triggers hidden queries.

    2D.5 Your options

    Strategy equals hashCode Good Bad Use when
    A. Default (identity) == identity Simple, safe within one session Detached copies and proxies are never equal Entities never compared outside one session
    B. Business key compares an immutable natural key (email, sku) hash of that key Stable in every state Needs a truly unique, never-changing, non-null key User.email, Product.sku (if they never change)
    C. Assigned UUID compares id id.hashCode() Id exists from construction, so stable Random UUIDs hurt index locality (consider time-ordered UUIDs) No natural key, or distributed id generation
    D. Generated id, null-safe, constant hash id != null && id.equals(other.id) a constant (the class hash) Works with DB-generated ids, stable hash All objects land on one rack, so large sets get slow Small child collections (tens or hundreds of items)
    E. All fields / Lombok default all fields all fields none Everything above Never for entities

    2D.6 Correct code

    Business key (User):

    java
    @Entity @Table(name = "users")
public class User {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "users_seq")
    @SequenceGenerator(name = "users_seq", sequenceName = "users_seq", allocationSize = 50)
    private Long id;

    @Column(nullable = false, unique = true, updatable = false)   // never changes after creation
    private String email;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof User other)) return false;            // instanceof works with proxies
        return Objects.equals(getEmail(), other.getEmail());      // use getters so proxies work
    }

    @Override
    public int hashCode() { return Objects.hashCode(getEmail()); }
}

    Generated id (OrderItem):

    java
    @Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof OrderItem other)) return false;
    return getId() != null && getId().equals(other.getId());   // two unsaved items are never equal
}

@Override
public int hashCode() {
    return getClass().hashCode();    // constant: never changes between new / managed / detached
}

    A small subtlety: a proxy and the real entity have different getClass(). If both can appear in the same set, use Hibernate.getClass(this).hashCode() or a fixed constant per entity class.

    Rules of thumb

    • If an immutable natural key exists, use it (B).
    • Otherwise use D for small collections, or C when ids are assigned at creation.
    • Never include associations or changing fields.
    • Keep toString() free of lazy associations.

    2D.7 Failure case: "ghost" items in a Set

    Situation. Order.items is a Set<OrderItem> with an id-based hashCode. A web flow adds items (id null), persists the order, and later calls order.getItems().remove(item).

    Symptoms. remove does nothing. Orphan removal doesn't delete the row. The cart shows duplicate lines.

    Diagnosis. A tiny test that prints item.hashCode() before and after persist(), and checks items.contains(item) both times. The values differ, and contains flips from true to false.

    Fix. Use strategy B, C or D. Add a unit test (no database) that proves hash stability across the new, managed and detached states, plus an integration test: add, flush, remove.

    Putting everything in Topic 2 together

    java
    @Service
@RequiredArgsConstructor
public class OrderService {

    private final OrderRepository orders;
    private final ProductRepository products;

    @Transactional                                   // read-write
    public OrderDto addItem(Long orderId, String sku, int qty) {
        Order order = orders.findById(orderId).orElseThrow();       // SELECT (or from the bench)
        Product p = products.findBySku(sku).orElseThrow();          // SELECT
        order.addItem(new OrderItem(p, qty, p.getPrice()));         // memory change
        order.recalculateTotal();                                   // memory change
        return OrderDto.from(order);                                // map to a DTO inside the transaction
    }   // commit: flush -> INSERT order_items; UPDATE orders SET total=?, version=? WHERE id=? AND version=?
}

@Service
public class OrderQueryService {
    @Transactional(readOnly = true)                  // no snapshots, no flush, BEGIN READ ONLY
    public Page<OrderSummary> list(Long userId, Pageable page) {
        return orders.findSummariesByUserId(userId, page);          // DTO projection (Topic 9)
    }
}

    Generated SQL for addItem:

    sql
    select ... from orders where id=?
select ... from products where sku=?
insert into order_items (order_id, product_id, quantity, unit_price, id) values (?,?,?,?,?)
update orders set status=?, total=?, user_id=?, version=? where id=? and version=?

    Two observations:

    • order.addItem(...) calls items.add(...), which loads the whole items collection first (one extra SELECT) because it is lazy. Many teams add children through their own repository instead. This is part of the lazy-loading story in Chapter 2.
    • The version bump happens because total changed. With optimistic locking, two concurrent addItem calls produce an OptimisticLockException instead of a silent lost update (Part 2).

    Performance summary for Topic 2

    Concern What helps
    Flush cost grows with persistence context size Smaller transactions, clear(), read-only mode, stateless or bulk approaches
    Dirty-check CPU Bytecode dirty tracking, read-only entities, loading fewer entities
    Large UPDATE statements @DynamicUpdate for wide rows only
    Hidden flushes before queries Read first, change later, or use FlushMode.COMMIT in controlled places
    Constant hashCode with big sets Keep association collections small, or use a business key

    Key takeaways (Topic 2)

    • Flush is not commit. Execution order is inserts, updates, collection changes, deletes, regardless of the order of your code.
    • AUTO flush looks at which tables a JPQL query touches. Native SQL flushes everything.
    • Dirty checking compares each managed entity with its load-time snapshot. Cost grows with the number of entities.
    • The default UPDATE writes all columns. @DynamicUpdate writes only changed ones but breaks statement reuse.
    • readOnly = true works in layers (Spring, Hibernate MANUAL flush, JDBC read-only, PostgreSQL). Writes can be silently dropped at the Hibernate layer.
    • In PostgreSQL, one failed statement aborts the whole transaction. You can't catch the error and continue.
    • Entity equals/hashCode must stay stable through all lifecycle states, work with proxies, and ignore associations. Prefer a business key; otherwise null-safe id equality with a constant hash.
